# 06 - 最佳实践

本教程的目标：了解插件设计的判断框架与架构演进方式——什么时候上浮、怎么沉淀、范式边界在哪。

## 1. 业务逻辑永远在插件里

```
❌ 写进壳（apps/）     → 换实现要改壳; 能力无法复用; 装配时被机制检查拦下
✅ 写进业务插件         → 三步法（能力/流程/声明）; 可挂载到任意应用
✅ 写进公共插件         → 通用能力; 被多应用共享; 有独立生命周期
```

判断一句话：**壳是"一次性代码层"，能力必须落在可复用层**。

## 2. 插件设计：协议化（可替换的根源）

消费方只依赖 **key + 协议形状**，不依赖实现：

```python
# 消费方（永远这样写）
svc = ctx.get("storage")

# 提供方换实现（只改这一处）
ctx.register("storage", MinioStorage())    # 之前是 FileStorage()
```

这就是"换存储/换引擎/换队列，消费方零改动"的根源——**消费方只认识 key，不认识实现**。

纪律：

- 消费纪律：**每次调用时 `ctx.get(key)`**，不要缓存引用（缓存了替换就失效）
- 能力面纪律：`provides` 必须覆盖 `apply` 里注册的全部 key（违反 → 装配报错）
- IO 纪律：能力里不直接写文件/连库——落盘走产物通道或数据通道

## 3. 上浮判断：三问

发现某个能力"可能通用"时，用三问判断（上浮原则）：

```
① 会不会被替换？   可能换引擎/换 DB/换实现 → 上浮（隔离变更）
② 谁会用？         ≥2 个业务/应用 → 上浮（复用）
③ 会不会拖垮宿主？ 大到牵一发动全身 → 上浮（保可演进性）
```

三条任一命中 → 考虑上浮。注意区分：

```
能上浮 ≠ 该上浮     promote 命令不拦任何插件（技术可行）
该上浮 ≠ 该进模板   上浮是生命周期声明; 模板只带走你上浮过的
```

**上浮 = 生命周期解绑**：

```
私有插件    生命周期 = 应用        卸载应用 → 随删
公共插件    生命周期 = 独立        卸载应用 → 保留; 只能单独卸
理想应用    无私有插件            卸载只删壳——能力全在可复用层
```

## 4. 模板沉淀飞轮（跨应用复用）

```
已完成应用（如 review）
  → 业务中发现的通用能力 promote 上浮
  → aic template 提取模板 = 基础 AIC + 公共插件 + 示例壳 hello_aic
  → 新项目从模板起步（开箱即用的 AI 应用地基）
  → 新项目又沉淀新的公共插件 → 模板越来越强
```

**模板永远不复制旧应用，只继承你上浮过的公共插件**——上浮就是传承声明。

## 5. 组织契约要点（机制强制项）

```
壳布局契约:  装配组 5 文件齐全 + 入口至少一个 + config 为目录
壳内容契约:  壳内自定义 .py 不得 import extensions.* / 定义 Plugin / 接线动作
任务名协议:  shell 注册的任务名必须与 worker 侧同名（跨进程契约）
插件区:      除地基（kernel/apps/tools）外一切目录皆可放插件; extensions/ 是惯例位
```

这些由机制强制（违反装配即报错），不是靠评审自觉——"大声失败"让问题在装配时暴露，
而不是冷路径才炸。

## 6. 部署前检查清单（多进程）

默认装配是**单进程兜底**（内存/本地实现），多进程部署（API + Celery worker）前逐项核对：

```
cache      MemoryCache（默认） → 多进程必须换 RedisCache（锁/运行态各自进程内存不共享）
jobs       ThreadJobQueue（默认）→ 多进程必须换 CeleryJobQueue（需 Redis broker 可用）
storage    LocalStorage（默认）→ 多进程共享依赖同一磁盘路径; 多机必须换共享存储实现
sessions   `SessionPlugin(runtime_dir=...)` 指定共享目录（默认临时目录; 跨进程 attach 靠目录存在恢复）→ 多机部署必须统一目录
```

构造注入即可替换（`CachePlugin(impl=RedisCache())`、`JobsPlugin(impl=CeleryJobQueue(...))`），消费方零改动。

## 7. 诚实的边界（0.1 版本验证基线）

```
已验证:  内核机制（m0~m5 全绿）/ 壳契约与任务名协议（m6）/
         工具链（m7）/ 工具闭环（真实跑通）
验证基线: fake 引擎全链路（默认）——真实 LLM 引擎端到端
         是 0.2 的迭代项
不承诺:  真实引擎/MinerU/MySQL 的端到端（插件已就位, 待真实环境验证）
```

## 总结

```
应用 = 组件组合（内核组织 + 插件接入）
插件 = 组件 + 插件声明（inject/provides/apply）
能力放插件（协议化）; 通用能力上浮（生命周期独立）
模板继承公共插件（飞轮沉淀）; 机制强制保护边界（大声失败）
跨盒 import 走 ctx 或声明（旁路契约, 装配期强制）
```
