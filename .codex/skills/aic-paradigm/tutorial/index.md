# AIComposer 教程

> **适用版本**: ai-composer 0.1.0
> **前置知识**: Python 3.11+ 基础

## AIComposer 是什么

AIComposer 是一个 AI 应用开发范式。它的核心公式只有一句话：

```
应用 = 平台内核 + 业务插件组合
```

## 为什么需要它（背景）

看两个典型 AI 业务应用的组成：

```
审查应用: 路由 + 审查逻辑 + 存储 + 队列 + LLM 引擎 + 会话管理
编写应用: 路由 + 编写逻辑 + 存储 + 队列 + LLM 引擎 + 会话管理
           └─────── 80% 一模一样 ───────┘   └─ 20% 不同 ─┘
```

过去每做一个新 AI 应用，这 80%（存储、队列、会话、SSE、沙箱……）都要重新写一遍——或者从老应用复制，连老应用的烂账一起复制。升级时更是"**只敢加、不敢删、不敢换**"：不知道改哪里，替换组件更不敢动。

AIComposer 的药方：

| 痛点 | 药方 | 落在哪 |
|---|---|---|
| 不敢删 | **可逆卸载**——挂载效果全部记账，卸载逆序撤销零残留 | kernel 效果桶 |
| 不敢换 | **契约替换**——消费方只依赖 key + 协议形状，换实现改注册一行 | 插件协议 |
| 不知道改哪 | **组合集中 + 能力面声明**——业务改动点集中在插件包内 | provides + 三步法 |

一句话：**把 80% 抽出来做成平台，开发者只写那 20%**。

## 三个角色

```
kernel/       平台内核（机制: 注册表/装配/事件）——不认识任何业务
extensions/   插件（能力: 业务功能与通用能力）——每业务一个
apps/         应用壳（组合: 这个应用要哪些插件、开什么入口）
```

**唯一属于你写的代码 = 业务插件**。内核是平台现成的，应用壳是搭积木（列清单）——业务插件就是"你的应用功能"本身。

## 教程约定

- 所有命令在项目根目录执行（`aic` 为安装后的命令；仓库开发模式下等价于 `python -m tools.cli`）
- 代码块后标注**预期输出**，方便对照
- `> **注意**` 提示常见误区
